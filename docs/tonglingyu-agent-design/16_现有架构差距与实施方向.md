# 16 现有架构差距与实施方向

本文只面向通灵玉 Gateway/Runtime，不把通用平台化能力或外部内容生产作为前置条件。当前目标是维护证据型 RAG 运行闭环：

`runtime DB -> 证据卡片 -> 证据包 -> reviewer 审校 -> 分层回答`

## 基线状态

本节记录进入第一版工程实现时的基线差距，不作为当前完成度来源。
当前实现进度以 `PROGRESS.md` 和
`20_Runtime接入设计与实施计划.md` 的 checklist 为准。

| 模块 | 状态 | 处理 |
| --- | --- | --- |
| 产品设计 | `00` 到 `15` 已导入 | 作为第一版目标依据 |
| runtime DB | 由仓库外流程准备 | 本仓库只做 schema migration、查询、证据包和治理 |
| Gateway | OpenAI-compatible 入口已存在 | 继续维护鉴权、会话、SSE、admin、metrics 和实时文本能力 |
| Runtime | 检索、证据包、reviewer、治理和 memory 表结构已存在 | 继续维护运行期 schema、规则 catalog 和工作流 |
| Open WebUI | 通过 Gateway 暴露 `tonglingyu` | Function/Action 代码保留在 `open-webui/functions/` |

外部内容生产不作为本仓库实现起点；本仓库只维护 runtime DB 读取和运行链路。

## 必补能力

| 能力 | 第一版要求 |
| --- | --- |
| 单一可见模型 | Open WebUI 只展示“通灵玉” |
| Gateway | 负责鉴权、会话、编排、安全、审计和 OpenAI-compatible 入口 |
| 内部 Agent | 四个 `honglou-*` profile |
| Runtime DB | 消费外部准备好的分层事实、索引和评测题库 |
| 证据卡片 | RAG 只返回可追溯证据，不直接生成最终回答 |
| 证据包 | Gateway 汇总证据并映射到结论声明 |
| reviewer | 复杂回答固定审校，不提供用户关闭开关 |
| 审计 | 记录追踪编号、调用顺序、证据包和审校结果 |
| 验证 | 建立 100 到 200 条标准问题和负面用例 |

## 数据边界

本地生成物写入 `data/tonglingyu/`，默认不提交。最小 SQLite/FTS 结构应覆盖：

- `sources`
- `editions`
- `chapters`
- `blocks`
- `blocks_fts`
- `rare_char_annotations`
- `commentaries`
- `versions`
- `people`
- `aliases`
- `relationships`
- `events`
- `poems`
- `terms`
- `evidence_cards`
- `evaluation_cases`
- `kb_version`

模型生成内容不得反写为 runtime 事实。风格资料不覆盖正文、脂批、版本或校订证据。
现代白话摘要只能辅助检索，不能作为可引用证据。

runtime DB 不是一个单一向量检索层。正文、脂批、版本、人物关系、事件、诗词判词和研究观点
必须分层；每张证据卡片必须包含支持范围和不支持范围。

## 实施顺序

1. 保持 runtime schema migration 可重复执行。
2. 保持 Gateway、内部 Agent profiles、证据包、reviewer 和审计可回归。
3. 保持 Open WebUI 只暴露“通灵玉”。
4. 扩展 SSE/WebSocket/Redis Streams 文本实时能力。
5. 对外部提供的 runtime DB 做 preflight、health、metrics 和 release gate。
