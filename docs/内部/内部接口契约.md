# 10 内部接口契约

## 目标

内部接口用于 Gateway、Agent Runtime、Runtime profile、证据检索服务、证据服务和
审校能力之间协作。本文档只定义语义契约，不绑定具体实现方式。

## 内部接口分组

<!-- markdownlint-disable MD013 -->
| 接口组 | 调用方 | 被调用方 | 目的 |
| --- | --- | --- | --- |
| Agent 调用接口 | Gateway | Agent Runtime Adapter | 调用指定 profile 或 step plan 执行任务 |
| Run/Response 归一化接口 | OpenAI handler、Run handler、WS handler | Run Manager | 把外部协议归一化为同一执行对象 |
| Response Event 接口 | Gateway handler、worker、SSE、WS | Response event store | 写入、读取和回放 response 生命周期事件 |
| Response Job 接口 | Gateway handler、worker | Redis Streams job queue | 创建、领取、重试、取消和 dead letter response job |
| Control/Action 接口 | Run handler、WS handler、worker | control stream / action store | 取消、恢复、人工审批和外部工具回调 |
| 上下文投影接口 | Gateway | Context Governance | 为不同 consumer 生成可见 context projection |
| 正文检索接口 | `honglou-text` 或 read-only tool | 证据检索服务 | 获取正文证据 |
| 脂批检索接口 | `honglou-commentary` 或 read-only tool | 证据检索服务 | 获取脂批证据 |
| 版本比较接口 | `honglou-commentary` 或 read-only tool | 证据检索服务 | 获取版本差异 |
| 人物事件查询接口 | Runtime profile 或 read-only tool | 证据检索服务 | 获取人物关系和事件链 |
| 证据包接口 | Runtime profile/tool，Gateway admin proxy | 证据服务 | 创建、读取、回放证据包 |
| 审校接口 | Runtime step plan | `honglou-reviewer` profile | 审查草稿 |
| 审计记录接口 | Gateway 与 Agent Runtime | 审计服务 | 写入追踪和调用日志 |

## Run/Response 归一化接口

### 目的

让 `/v1/chat/completions`、`/v1/responses`、原生 `/v1/runs` 和 WebSocket
`response.create` 归一化为同一 canonical 执行对象，避免多个入口维护多套状态机。
第一版外部可以继续以 `response_id` 为主要公开主键，但内部必须先分配并持久绑定
`run_id -> response_id -> chat_completion_id` 投影，且任意两个 ID 不能代表不同 workflow。

### 输入语义

1. 外部协议类型：`chat_completions`、`responses`、`run` 或 `realtime_ws`；
2. 可见模型或受控 graph/profile 别名；
3. 用户输入、messages 或受控 task payload；
4. 鉴权后得到的 tenant、user、subject 和 session；
5. 客户端 metadata，仅作关联信息；
6. 幂等键；
7. stream/background/timeout/priority；
8. callback 配置引用；
9. 公开 response format；
10. forbidden control field scan 结果。

### 输出语义

1. `run_id`；
2. `response_id`；
3. 可选 `chat_completion_id`；
4. `session_id`；
5. `trace_id`；
6. 归一化后的 Runtime workflow input；
7. 允许的 tool/profile policy digest；
8. 初始状态；
9. events/control stream ref；
10. owner-only access scope；
11. safe point policy；
12. 关键事件持久化策略。

### 验收标准

1. 同一个幂等键不能创建两个执行对象；
2. metadata 中的 `tenant_id`、`thread_id` 不能覆盖鉴权事实；
3. OpenAI-compatible、Responses、Run 和 WS 查询同一对象时状态一致；
4. 用户输入中的 profile、tool policy、reviewer、context、memory、trace 覆盖字段必须被拒绝；
5. Runtime workflow input 只能由 Gateway 归一化器和 policy engine 构造；
6. Run API 不能绕开 evidence package、reviewer、audit 或 context governance；
7. run/response/chat id 映射缺失、冲突或幂等命中不一致时必须 fail-closed；
8. 归一化接口未成功返回前，handler 不能写 job queue、event stream 或 final journal。

## Response Event 接口

### 目的

把 chat、responses、WebSocket 和后台 worker 的输出统一为 `ResponseEvent`，使 SSE、
WS、status、replay 和 admin trace 使用同一条事件源。详细实施见
`../架构/Gateway_Realtime_Redis_Architecture.md`。

### 输入语义

1. `response_id`；
2. `session_id`；
3. `trace_id`；
4. 当前状态；
5. 事件类型；
6. 事件 payload；
7. public/admin 可见性；
8. 上一个 sequence；
9. 可选 evidence package ref；
10. 可选 final response ref。

### 输出语义

1. 新事件编号；
2. 新 sequence；
3. Redis stream id；
4. 更新后的 response state；
5. 写入结果或 typed error。

### 验收标准

1. 单个 response 内 sequence 严格递增；
2. 事件追加和 state 更新必须原子化；
3. public projection 不包含 admin-only 字段；
4. `completed`、`failed`、`canceled` 终态不能回退；
5. SSE 和 WS 只能读取 public event；
6. 断线后可从指定 event id 后 replay；
7. Redis 写入失败不能伪造成成功回答。

## Response Job 接口

### 目的

用 Redis Streams 管理后台长任务、worker retry、取消、恢复和 dead letter，避免
WebSocket 在线连接承担可靠性。

### 输入语义

1. response 编号；
2. session 编号；
3. trace 编号；
4. 归一化后的用户问题；
5. 原始外部 message id 或幂等键；
6. 调用方 subject；
7. context request refs；
8. 最大证据数和超时；
9. worker attempt；
10. cancel flag。

### 输出语义

1. job 入队结果；
2. consumer group 领取状态；
3. worker lease；
4. retry 或 dead letter 状态；
5. response event stream。

### 验收标准

1. worker crash 后 pending job 可被 reclaim；
2. transient error 可 retry；
3. schema/auth/model 错误不 retry；
4. 取消请求能被 worker 安全点观察；
5. 达到最大 attempt 后进入 dead letter；
6. job 执行不能绕过 evidence package、reviewer 和 audit。

## Control/Action 接口

### 目的

把取消、恢复、人工审批、外部工具回调和追加输入写入同一 control/action 通道，由
worker 在安全点读取。HTTP handler 或 WebSocket handler 不能直接改写最终答案或
Runtime 内部状态。

### 输入语义

1. `run_id` / `response_id`；
2. action 编号或 control event 编号；
3. 调用方 subject；
4. control 类型：`cancel`、`resume`、`submit_action`、`append_input`；
5. 幂等键；
6. action payload；
7. 过期时间；
8. 权限 scope；
9. 当前 expected status；
10. 审计原因。

### 输出语义

1. control event stream id；
2. action 状态；
3. 新 response status；
4. 是否已被 worker 观察；
5. typed error。

### 验收标准

1. cancel 只设置 cancel/control 状态，由 worker 在安全点生效；
2. action submit 必须校验 assignee、tenant、过期时间和幂等键；
3. 重复 action submit 返回已有结果，不能重复执行副作用工具；
4. 终态 run 拒绝新的 action；
5. append input 只能进入允许追加输入的状态；
6. control/action payload 不能包含 raw prompt、密钥、内部 policy 明文或未脱敏工具结果；
7. 所有 control/action 都必须写 audit。

## Agent 调用接口

### 目的

让 Gateway 以受控方式调用 Agent Runtime，执行指定 consumer/profile 或已授权的
Runtime step plan。

### 输入语义

1. 追踪编号；
2. 会话编号；
3. 目标 consumer/profile；
4. 任务名称；
5. 任务输入；
6. 工具权限约束；
7. 超时和重试策略；
8. 输出格式要求；
9. schema version；
10. profile step 依赖和 output_ref；
11. `context_pack_ref`；
12. `context_pack_schema_version`；
13. `context_pack_digest`；
14. `context_projection_ref`；
15. `context_projection_schema_version`；
16. `context_projection_digest`；
17. `consumer_type`；
18. `consumer_name`；
19. `runtime_adapter`；
20. `tool_policy_digest`；
21. `output_contract_digest`。

### 输出语义

1. 任务状态；
2. 结构化结果；
3. 调用摘要；
4. 错误类别；
5. 运行时长；
6. 是否符合 schema；
7. RuntimeStreamEvent 或最终 RuntimeOutput；
8. evidence/package ref。

### 验收标准

1. 用户不能直接构造该接口请求；
2. consumer/profile 只能执行被授权任务；
3. 输出不符合 schema 时必须拦截；
4. 超时必须被 Gateway 处理；
5. Gateway 不能通过请求字段给 Runtime profile 扩权；
6. 内部 profile 不能作为 Open WebUI 可见模型暴露；
7. `context_pack_ref` 或 `context_projection_ref` 缺失、schema 不支持、digest
   不匹配、consumer 不匹配或 Runtime Adapter 不匹配时必须 fail-closed；
8. Runtime step plan 的 allowed tools 必须与 `tool_policy_digest` 绑定；
9. 当前 Context Projection Runtime 只接受 `consumer_type=runtime_profile` 和已登记 `honglou-*`
   consumer；未知 consumer 与 `external_agent` 必须 fail-closed。

## 上下文投影接口

### 目的

为不同 Runtime consumer 生成不同可见上下文，避免信息过载和权限混乱。
详细对象、scope、journal 和 memory 边界见
`../子模块/Scoped_Context与受控Memory.md`。

### 输入语义

1. 用户问题；
2. 会话摘要；
3. consumer 类型；
4. 任务类型；
5. 策略约束；
6. `interaction_context_id`；
7. scope binding；
8. memory read policy；
9. `consumer_name`；
10. `runtime_adapter`。

### 输出语义

1. 该 consumer 可见的问题内容；
2. 必要的上下文摘要；
3. 禁止使用的上下文范围；
4. 可调用 read-only tools 列表；
5. 输出约束；
6. `context_pack_id`；
7. `context_pack_ref`；
8. context pack schema version 和 digest；
9. `context_projection_id`；
10. `context_projection_ref`；
11. context projection schema version 和 digest；
12. `consumer_type`、`consumer_name` 和 `runtime_adapter`；
13. `tool_policy_digest` 和 `output_contract_digest`；
14. session journal ref。

### 验收标准

1. text consumer 不获得完整用户历史；
2. commentary consumer 不获得无关正文库原始数据；
3. reviewer 只获得草稿和证据包；
4. main 获得必要上下文但不直接获得数据库权限；
5. 外部用户不能指定 context、scope、memory 或 tool policy；
6. memory ACL 不匹配时必须 fail-closed；
7. context pack 与 context projection 可按 trace 回放，但不向普通用户暴露；
8. Runtime profile 只能读取自己的 projection，不读取完整 context pack；
9. 未知 consumer、未知 Runtime Adapter 和 `external_agent` 在
   Context Projection Runtime 必须 fail-closed。

## 正文检索接口

### 输入语义

1. 检索问题；
2. 人物、回目、版本、段落类型等条件；
3. 返回数量；
4. 是否需要原文片段；
5. 是否需要支持范围和不支持范围。

### 输出语义

1. 正文证据卡片；
2. 回目和位置；
3. 原文片段或摘要；
4. 支持范围；
5. 不支持范围；
6. 置信度。

### 验收标准

1. 必须返回来源；
2. 不返回无来源概括；
3. 不混入脂批；
4. 未命中时返回证据不足。

## 脂批检索接口

### 输入语义

1. 检索问题；
2. 版本条件；
3. 回目或人物条件；
4. 批语类型；
5. 是否需要对应正文。

### 输出语义

1. 脂批证据卡片；
2. 批语版本；
3. 对应正文位置；
4. 批语类型；
5. 支持范围；
6. 不支持范围；
7. 置信度。

### 验收标准

1. 必须标注版本；
2. 必须说明对应位置；
3. 不得将脂批作为正文事实返回；
4. 无法定位来源时标记证据不足。

## 证据包接口

### 目的

将证据卡片、结论声明和审校记录统一管理。
目标 Runtime 接入后，证据包创建、读取和 replay 由 Runtime Agent/tool 侧执行；
Gateway 只保存 package ref 或提供 admin proxy。

### 输入语义

1. 用户问题；
2. 证据卡片；
3. 结论声明；
4. 追踪编号；
5. 生成阶段；
6. Runtime profile step 和 output_ref。

### 输出语义

1. 证据包编号；
2. 证据卡片列表；
3. 结论声明列表；
4. 证据等级；
5. 审校状态；
6. replay ref。

### 验收标准

1. 每个复杂回答都有证据包；
2. 每条关键结论能映射证据；
3. 证据包可追溯到请求；
4. 证据包不可被普通用户任意篡改；
5. replay 不依赖上游模型。

## 审校接口

### 输入语义

1. 用户问题；
2. 草稿答案；
3. 证据包；
4. 回答策略；
5. 负面清单。

### 输出语义

1. 是否通过；
2. 问题列表；
3. 严重程度；
4. 必须修订项；
5. 可保留结论；
6. 审校摘要。

### 验收标准

1. 无证据断言必须被拦截；
2. 脂批和正文混淆必须被拦截；
3. 前八十回和后四十回混淆必须被拦截；
4. 版本缺失必须至少警告；
5. 用户不能关闭审校。

## RAG 内部接口

证据检索服务相关内部接口应按证据类型拆分，而不是提供一个无差别的大检索接口。

| 内部能力 | 目的 |
| --- | --- |
| 原文证据检索 | 查询正文、回目、段落、诗词、判词、曲文 |
| 脂批证据检索 | 查询批语、批语类型、批语版本和对应正文 |
| 版本边界查询 | 查询版本系统、存回范围、来源状态和使用限制 |
| 人物别名解析 | 将称谓、别名、号映射到标准人物 |
| 人物关系查询 | 查询人物关系及其证据等级 |
| 事件链查询 | 查询人物经历、事件前因后果和主题标签 |
| 字形读音查询 | 查询生僻字、异体字、旧字形和可追溯读音 |
| 证据卡片规范化 | 将不同来源结果整理为统一证据卡片 |
| 证据包创建 | 汇总证据卡片和结论候选 |
| 不支持范围校验 | 检查草稿是否滥用了证据 |

所有证据检索服务结果必须返回证据类型、来源、支持范围、不支持范围、校验状态和置信度。不得只返回自然语言概括。
